# PAI DSW H20：盘、OSS、各机环境（OpenWAM）

维护日期：2026-09-28。格式沿用 JEPA-WAM 仓库的 `docs/h20.md`，内容只写本项目实测过的部分。

训练和评估走 SSH Host 别名 `dsw-1` … `dsw-8`、`dsw-share1`。本项目实际用过 dsw-1、dsw-2、dsw-share1（均为 8×H20，约 96 GiB/卡），其余机器未确认。
仓库里只写这些别名，不写展开后的主机、端口、密钥。

**机器没有固定分工。** 这些机器和别的组共用，动手前先看清楚卡上是谁的进程；
不是自己起的进程不要杀，8 卡任务不要往已经有人占卡的机器上压：

```bash
nvidia-smi --query-gpu=index,memory.used,utilization.gpu --format=csv   # 卡空不空
ps -eo pid,user,etime,cmd --sort=-etime | grep -Ei 'python|train|eval' | head  # 谁的进程在跑
df -h /                                                                 # 盘还剩多少
```

路径和 Python 栈相对稳定，占用天天变。占用只写在文末快照里，**快照过期就按上面的命令重查**。

## 通用约定

- **系统 Python，没有 conda / venv。** 不同机器的版本不一样，用前先查：
  - dsw-1 / dsw-2：torch 2.10.0，deepspeed 0.18.9，flash_attn 2.8.3，依赖齐全，可以直接训练。
  - dsw-share1：Python 3.10.19，torch 2.9.1+cu130。原本没有项目依赖，2026-09-28 已用
    `pip install -c <(echo torch==$(python3 -c 'import torch;print(torch.__version__)')) -e .`
    （阿里云镜像）装好，**不要让 pip 升级 torch**。没装 flash_attn，注意力会退回 PyTorch SDPA，评估够用；
    训练前再决定要不要编译 flash_attn。
- **pip 走阿里云镜像**：`-i https://mirrors.aliyun.com/pypi/simple/`。pytest 默认没装，跑测试前先 `pip install "pytest>=8,<10"`。
- **训练输出必须放本地盘**（`/root/...`）。在 ossfs 上存 safetensors 会报
  `Operation not supported (os error 95)`，训练卡在保存那一步。
- **wandb 没登录**，训练设 `WANDB_MODE=offline`。
- **不要在服务器上做 git 操作。** 代码从本机按已跟踪文件清单 rsync 到隔离目录：
  ```bash
  git ls-files --cached --others --exclude-standard | while read f; do [ -f "$f" ] && echo "$f"; done > /tmp/mf.txt
  rsync -a --files-from=/tmp/mf.txt ./ dsw-X:/root/<目录>/
  ```
  `third_party/cosmos-predict2.5` 是 git 子模块，通用的远端验证脚本会因此拒绝执行，所以用上面的手动方式。
- **长任务用 `setsid nohup ... & disown` 起**，不依赖 SSH 会话保持连接（SSH 断线很常见）。
- **远端 `pkill -f` 会匹配到自己**：`ssh host 'pkill -f eval_offline.py; ...'` 会把这条 ssh 命令本身杀掉（exit 255）。
  模式里用方括号：`pkill -f "[e]val_offline.py --ckpt"`。
- 远端不能用前台 `sleep` 长等；等待条件用 `until <检查>; do sleep 15; done`。

## 训练速度（dsw-2 实测，2026-09-27）

8 卡、每卡 batch 24、梯度检查点开启，每步约 8.2 s：

| 阶段 | 耗时 | 备注 |
|---|---|---|
| umT5-XXL 文本编码 | 1.2 s | 开 `training.prompt_embed_cache_size` 后几乎为 0（G1 只有 360 条 prompt） |
| VAE 视频编码 | 1.7 s | 要省只能预编码，需要 TB 级存储，未做 |
| DiT 前向 | ~1.6 s | |
| 反向（含重算） | 3.6 s | 关梯度检查点在每卡 batch 24 和 16 下都显存溢出，**必须开** |
| 优化器 / 梯度同步 | ~1.7 s | |

数据加载不是瓶颈：每个 rank 8 个 worker 每 1.75 s 就能出一个 batch。

离线评估（`scripts/eval_offline.py`，10 步去噪、SDPA）：每个窗口约 0.5 s，单卡显存约 25 GB。
8 卡分片评估 1300 个窗口约 15 分钟（含加载 24 GB 权重）。

## 三块盘，用途不同

| 挂载 | 后端 | 用途 |
|---|---|---|
| `/`（含 `/root`） | 实例本地盘，数 TB | **训练输出 / checkpoint / 代码**。实例释放后会丢失。 |
| `/mnt/workspace` | 30 GB 云盘 | 容易占满，不放仓库、权重和数据。 |
| `/mnt/data` | ossfs，共享 OSS | **跨机持久副本和交接**。顺序 `cp` 可以（24 GB checkpoint 约 1–2 分钟）；不能用作训练输出目录。 |

## 路径

| 路径 | 内容 |
|---|---|
| `/mnt/data/models/OpenWAM-Alpha-Pretrain-Foundation-Model/` | 预训练基座（`checkpoint_step_154000.safetensors`，24.8 GB）+ `config.yaml` + `tokenizer/` |
| `/mnt/data/datasets/Unitree_G1_Dex1/` | G1-Dex1 数据（65 个可用的 v3.0 躯干系末端位姿任务） |
| `/mnt/data/chongzheng/openwam_g1/g1_dex1_normalization_stats.npy` | G1 共享归一化统计量（只用训练集计算） |
| `/mnt/data/chongzheng/openwam_g1/ckpts/stepN/` | mid-train checkpoint 的持久副本（带 `.done` 标记表示复制完成） |
| dsw-1 `/root/openwam_g1/runs/2026-09-27_11-35-37/` | G1 mid-train 输出，只保留最近 3 个 checkpoint |
| dsw-1 `/root/openwam_g1_logs/midtrain.log` | mid-train 日志 |
| dsw-share1 `/root/openwam_eval/` | 评估用代码副本 |
| dsw-share1 `/root/eval/stepN/summary.json` | 各 checkpoint 的离线评估结果 |

**checkpoint 放本地盘，出一个就复制一个到 OSS**：训练用 `keep_last_k_ckpts` 滚动删除旧的，
G1 mid-train 的 step 2000 和 4000 就是这样丢的，验证曲线缺了这两个点。

## 跨主机同步

- DSW 之间走 OSS 中转：产出机 `cp` 到 `/mnt/data/chongzheng/...`，消费机再 `cp` 到自己的 `/root`，
  8 个进程同时从 ossfs 加载权重会很慢。
- 目前在跑的自动化：
  - dsw-1 `/root/ckpt_sync.sh`：新 checkpoint 写完 2 分钟后复制到 `ckpts/stepN/`，训练结束后退出。日志 `/root/ckpt_sync.log`。
  - dsw-share1 `/root/eval_watch.sh`：发现 `ckpts/stepN/.done` 就跑 8 卡评估并汇总，评估完 step 20000 后退出。日志 `/root/eval_watch.log`。

## SSH 故障

- `Host key verification failed`：新机器第一次连接，需要用户在自己的终端里手动 `ssh <别名> hostname` 确认指纹。
- `Load key ...: invalid format`：私钥文件末尾缺换行。`echo >> <私钥>` 后用 `ssh-keygen -y -f <私钥>` 验证。
